# External review — Claude (2026-07-25)

> Reviewer had a working toolchain and tested consent-gate behavior empirically
> against dialoguer's source.

This is a genuinely solid build for a portfolio piece — the classifier's local/target-failure split and the histogram design in particular are well-reasoned. But there are real bugs, and one architectural landmine. Ranked below, with file/line, concrete failure, severity, and smallest fix.

## 1. [HIGH] The "fantasy RPS" fix only landed for HTTP — every one-way flood vector still has it

src/engine/udp_flood.rs:62-67, dns_flood.rs:119-123, icmp_flood.rs:81-85, raw.rs:122-126 (shared by syn/ack flood):
```
metrics.requests_sent.fetch_add(1, Relaxed);
match sock.send(&payload).await {
    Ok(n) => {
        metrics.bytes_sent.fetch_add(n as u64, Relaxed);
        metrics.responses_ok.fetch_add(1, Relaxed);   // <-- this is a send(), not a response
    }
```

This is exactly the bug you just fixed in http_flood.rs, re-introduced everywhere the fix didn't reach. `responses_ok` there means "local send() syscall returned Ok" — nothing to do with the target. For UDP/DNS/ICMP/SYN/ACK there is no read-back at all (raw.rs even discards `_rx`), so:

- The sampler's `rps = d_ok / interval` (mod.rs:795) reports egress packet rate, not delivered/effective load, for every raw-L4-only run — the exact "fantasy" pattern, moved one layer down.
- `error_rate` for these vectors reads ~0% even against a completely black-holed target, because a local UDP/raw send essentially never fails.
- In RunMode::Adaptive, this feeds govern()'s error-rate distress check (mod.rs:727-738): a raw-socket vector in Adaptive mode will never back off no matter how badly the target is failing, because its "error rate" measures "did my own NIC accept the write."

Concrete failure: run dns preset (DnsFlood + UdpFlood) against a target whose DNS resolver is completely down. Every send() succeeds locally, responses_ok climbs at full rate, the collapse curve shows a flat healthy-looking RPS line. The verdict ends up right (health probe catches it since l7_active is false), but the metrics the operator stares at (RPS, error rate) are silently lying — a real fantasy-RPS bug in the vectors that most need honest numbers.

Fix: rename responses_ok semantics per-vector, or split into sent_ok (local syscall success) vs confirmed (target-observed effect). For UDP/ICMP/SYN/ACK there usually is no confirmed-completion signal by design — the RPS line should be suppressed/labeled "send rate (unconfirmed)" or driven off the health probe's connect-latency signal. Don't reuse responses_ok for two meanings across vectors.

## 2. [HIGH] RunMode::Adaptive throttles per-vector off a run-global counter

src/engine/mod.rs:186-193 spawns one Governor + one govern() task per vector, but every govern() reads the same shared Arc<Metrics> (metrics.responses_ok / metrics.errors, mod.rs:727-728). There's exactly one Metrics for the whole run (mod.rs:166), not one per vector.

Concrete failure: the api preset is H2Flood + H2RapidReset + Rudy, all Adaptive. If Rudy starts racking up transport errors against a target that's fine for everything else, H2Flood's governor reads the same global error-rate spike and cuts its own concurrency in half (mod.rs:740-741) — throttling a vector doing nothing wrong. Conversely, a healthy H2Flood stream of completions can mask a distressed Rudy's error rate in the shared ratio, so Rudy never backs off. The "back-off/regrow cycle doubles as a recovery-time detector" framing is only true for single-vector runs; for any mixed preset it measures cross-contaminated noise.

Fix: give each vector plan its own Metrics (or at least its own responses_ok/errors), and have govern() read only its vector's counters. The global aggregate can still exist for the classifier.

## 3. [HIGH] Design contradiction: the CLI advertises Tor/SOCKS5 proxying for a tool whose safety model is "one attributable source IP"

auth.rs:19-21 — the legal notice states as a non-negotiable invariant: "All traffic originates from THIS machine only... The single source IP means every byte is attributable to you." But cli.rs:112-124 prompts every interactive operator: "Route through a proxy (e.g. Tor SOCKS5 127.0.0.1:9050)?", collects a ProxyConfig{url}, stores it on RunConfig, prints it in the summary (cli.rs:343-344).

It's currently a dead field (never read by engine::net::Target or any worker), so today it's a no-op. That's precisely what makes it dangerous rather than harmless: a fully-built UX affordance with a Tor default, one connect() call from being wired in by whoever picks up db.rs/web/ next — and nothing flags that doing so would invalidate the attributability invariant. An adversarial operator who wants to defeat single-origin attribution sees an explicit first-class prompt inviting exactly that.

Fix: remove the proxy prompt/field until it's a reviewed feature; or if genuinely wanted (testing your own infra from behind your own corporate proxy), rename away from "Tor SOCKS5" and add an explicit second consent line about non-attributability. Don't let "single-origin, always attributable" coexist silently with a shipped Tor-shaped prompt.

## 4. [MEDIUM] Health-probe errno constants are Linux-only, silently wrong on other Unixes

mod.rs:514-518:
```
const EMFILE: i32 = 24;
const ENFILE: i32 = 23;
const EADDRNOTAVAIL: i32 = 99;
const ENOBUFS: i32 = 105;
const ECONNREFUSED: i32 = 111;
```
These are Linux values. On macOS/BSD, ECONNREFUSED is 61, EADDRNOTAVAIL 49, ENOBUFS 55, ENFILE 41. No `#[cfg(target_os)]` guard, so on macOS every local-exhaustion errno falls through to `_ => ProbeOutcome::TargetFail` (mod.rs:567) — the exact self-inflicted-false-DOWN bug you just fixed comes right back on macOS.

Fix: gate behind `#[cfg(target_os = "linux")]` with a macOS/BSD variant, or better, match on `e.kind()` (std::io::ErrorKind::ConnectionRefused is stable and portable) and only fall back to raw errno for local-exhaustion cases without a stable ErrorKind.

Also: your tcp_abort_on_overflow question is correct and unaddressed — a target whose accept queue is full under your SYN flood can RST (not just drop-and-timeout), and that RST is indistinguishable from "closed port, healthy otherwise" (ProbeOutcome::Refused, not-a-failure). An overloaded target dying via RST reads as "up." Cheap partial fix: track baseline-Ok → load-Refused transition (currently thrown away; probe_baseline only keeps successful connects, classify.rs never compares Refused-rate against baseline).

## 5. [MEDIUM] recon target ≠ actual flood target in one edge case → silent baseline loss

main.rs:183-201: if recon runs and the operator picks "(keep original target)" (select_target returns None), ctx.baseline_ms is looked up by searching report.ranked_endpoints for e.url == chosen (main.rs:194-198) where chosen is the original cfg.target. Recon's ranked list is built from crawled endpoints — the typed target URL often won't appear verbatim (different path, trailing slash, scheme normalization). In that common case ctx.baseline_ms silently becomes None, and derive_outcome/classify fall back to "earliest low-error sample" (mod.rs:825-830, classify.rs:206-211) — not a crash, but a quiet accuracy loss. Worth a `debug!("recon baseline not found for kept target")`.

## 6. [LOW-MEDIUM] Hardcoded PRESET_CONCURRENCY = 2700 — your doubt is justified

presets.rs:16. Tuned against your router test's ulimit/ephemeral-port range; not adaptive. A stock Linux desktop (ulimit -n 1024) or default macOS (256) running a multi-vector preset (web: 4 × 2700 = 10,800 sockets) blows past local fd limits before meaningfully stressing most targets — the exact failure mode the probe_local_inconclusive guard exists to paper over, except now it produces Unknown/low-confidence verdicts on ordinary machines instead of real findings.

Fix: at startup read getrlimit(RLIMIT_NOFILE) (or the rlimit crate) and cap/warn at ~soft_limit / (vectors_in_preset * 1.5). Even a pre-flight "you have N fds, this preset wants M" message fixes most false-Unknown cases for free.

## 7. Consent gate / single-origin — no bypass found, one thing confirmed empirically

Checked against upstream: auth::require_consent() calls dialoguer::Input::interact_text(), which on non-TTY stdin (term.is_term() false) returns Err(NotConnected) immediately — confirmed against dialoguer's source, not just the doc comment. So "TTY-only, cannot be piped" holds: `echo "I HAVE AUTHORIZATION" | ./opennetbench` fails the gate, doesn't silently pass. The obvious caveat (your own comment frames it as "a deliberate friction point, not a security control") is that a pty-wrapped automation can satisfy any TTY check — true of any TTY gate, not a bug here.

No spoofing/amplification/reflection path found — every vector uses the host's own socket or real source IP (raw.rs local_src_ipv4). The one latent gap is #3 (the dead proxy field).

## 8. Good, briefly

- The local/target-failure split in classify.rs and its test suite (local_socket_exhaustion_does_not_read_as_target_down, etc.) is the strongest part of the codebase.
- histogram.rs's bucket math is correct and bounded (the mag − SUB_BITS underflow case is unreachable due to the early-return guard, and idx.min(N-1) bounds the top). No panics found.
- http_flood.rs's throttle/keep-alive/drain logic is implemented correctly — the Ok(false) vs Err(()) split cleanly separates "server told us to close" from "transport broke," and only the latter is backed off. This is the one vector where the metric-honesty fix is done right; it just needs to be extended to the others (finding #1).

## On résumé/design framing

The state-table-exhaustion thesis is sound. The single biggest credibility booster: fix #1 and #2 together — right now the headline feature (an "intelligent verdict") is trustworthy only for HTTP-shaped vectors; a reviewer who tries the router/dns presets (pure L3/L4) first sees a governor and RPS display that don't mean what they claim, before ever reaching the well-built classifier underneath. Ship the vector-scoped metrics fix and the per-vector governor fix before anything else.
