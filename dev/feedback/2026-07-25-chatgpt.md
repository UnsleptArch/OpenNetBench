> environment; findings are source-level, not compiler/test-confirmed).

I reviewed the uploaded repository statically: src/, Cargo.toml, DOCUMENTATION.md, README.md, and the engine/recon/classifier code. I also inspected the working-tree changes for the three recent fixes.

I could not run cargo test because the review environment does not have cargo installed, so the findings below are source-level findings rather than compiler/test-confirmed findings.

## Bottom line

The project has a genuinely interesting thesis: single-origin resilience testing should measure state exhaustion and service behavior, not pretend to be a DDoS cannon. The independent probe and evidence-bearing classifier are the right direction.

But the current implementation has several serious problems:

- The shutdown guarantee is not actually safe.
- The classifier can call slow-connection L7 attacks Healthy.
- ECONNREFUSED handling is too optimistic for a service-health probe.
- The new completion-based metrics mix incompatible meanings across vectors.
- 2700 workers is not defensible as a universal fixed pressure level.
- The configured proxy is silently ignored.
- The documented "sustained" degradation logic is not sustained.

## P0 — shutdown is not guaranteed to stop traffic

src/engine/http_flood.rs:87-95, :118-121
src/engine/h2_flood.rs:62-66
src/engine/h2_rapid_reset.rs:58-65

Failure: Ctrl-C triggers `wait_for_stop()` → `shutdown.trigger()` → await every worker. But several workers can be stuck in operations that do not race the shutdown channel.

Concrete scenario:
1. Target accepts a TCP connection.
2. HTTP worker sends a request.
3. Target stops responding but keeps the TCP connection open.
4. `one_request()` blocks indefinitely in `conn.read_buf(buf).await`.
5. User presses Ctrl-C.
6. `shutdown.trigger()` fires.
7. `run()` waits for the worker.
8. The worker cannot observe shutdown because it is stuck inside `read_buf()`.

Same structural problem exists in H2: `resp_fut.await` and potentially `send_req.ready().await`. The process can remain alive and the traffic can continue after the operator has attempted to stop it. That directly contradicts the safety model's implied guarantee: stop the process, stop the traffic.

Severity: P0 — safety/correctness

Smallest correct fix: Every potentially unbounded network operation needs cancellation:
```
tokio::select! {
    result = conn.read_buf(buf) => { ... }
    _ = shutdown.changed() => return,
}
```
For every worker, additionally impose a bounded shutdown drain in run(): trigger shutdown, wait grace period, abort remaining tasks. Do not rely on cooperative cancellation alone — it is exactly what fails when a future is stuck waiting on a peer.

## P0 — the consent gate does not explicitly enforce the claimed TTY-only property

src/auth.rs:25-32

The requirement is: TTY-only and cannot be piped. The implementation is `let entered: String = Input::new().interact_text()?;` — there is no explicit terminal check. Even worse, `if entered.trim() != CONSENT_PHRASE` means `I HAVE AUTHORIZATION` with leading/trailing whitespace is accepted, which is not "verbatim."

Severity: P0 under your stated non-negotiable safety model

Smallest correct fix: Explicitly reject non-terminal input before asking for consent:
```
use std::io::IsTerminal;
if !std::io::stdin().is_terminal() {
    bail!("authorization requires an interactive TTY");
}
```
Then compare exactly (after the input API strips the line terminator): `if entered != CONSENT_PHRASE { bail!(...) }`. Do not assume dialoguer's interaction behavior is equivalent to your security invariant. Enforce the invariant yourself.

## P1 — slow L7 vectors are classified as L4-only and can be reported Healthy after damaging the service

src/engine/mod.rs:470-475 — `l7_active` only matches HttpFlood | HttpsOnly | RangeFlood | H2Flood. This excludes Slowloris, Rudy, SlowRead, TlsExhaust, H2RapidReset, H2Continuation — several of which are absolutely application/protocol-layer attacks.

Concrete failure: run only Slowloris. Target has 2,700 held connections, exhausted worker pool, starts returning service errors to ordinary clients. But the independent TCP probe still succeeds. Classifier receives `l7_active = false`, probe = stable, returns Healthy ("target kept accepting connections — absorbed"). That is a false negative — a target can accept TCP connections while its HTTP service is completely unusable.

Severity: P1 — missed finding

Smallest correct fix: stop using one boolean. Use capability-specific signals (has_http_status_signal, has_request_latency_signal, has_connection_hold_signal, has_protocol_signal). For slow-connection vectors, use evidence such as held connections, connection-acceptance failure, TCP connect latency, or a separate control request from an independent client. The current health probe is not sufficient to establish HTTP service health.

## P1 — ECONNREFUSED is incorrectly treated as "healthy enough" after a successful baseline

src/engine/mod.rs:518-527, :564-567; src/classify.rs:137-191

`ECONNREFUSED → Refused → not a failure` is defensible for "is the host reachable and actively rejecting this TCP connection?" It is not defensible for "is the target service still accepting connections?"

Concrete failure: baseline probe succeeds on port 80. Load begins. Target becomes overloaded, listener starts actively rejecting with RST. Probe receives ECONNREFUSED for every subsequent check → probe_failures == 0 → classifier can report Healthy. The service is no longer accepting connections, but the code calls that "not a failure."

Severity: P1 — missed outage/degradation

Smallest correct fix: track baseline state. baseline accepted + later ECONNREFUSED → service-side failure/degradation. baseline refused → don't call it a new failure. baseline unknown → Unknown. Keep host-level interpretation as evidence but don't confuse "host is alive" with "service is healthy." Also, ECONNREFUSED is not universally guaranteed to mean the remote sent an RST; local policy/network namespaces can also produce it — the current comment overstates certainty.

## P1 — the new RPS/error accounting is still semantically inconsistent

src/engine/mod.rs:785-800; http_flood.rs:163-185; udp_flood.rs:62-70; raw.rs:122-129

The change from requests_sent to responses_ok was correct for the original HTTP bug, but the new global counters are used for fundamentally different things.

HTTP: this sequence is broken — request sent → headers arrive → responses_ok++ → body drain fails → errors++. One logical operation is now both completed=1 and error=1, so `error_rate = errors/(responses_ok+errors)` is not a true per-request error rate.

Smallest fix: separate attempts_started / responses_completed / transport_failures / body_drain_failures; define exactly what the reported rate means (request_completion_rate vs transport_failure_rate).

UDP/raw: `sock.send()` success increments responses_ok, but that just means the local kernel accepted the datagram. Against a black-holed target: local send succeeds, responses_ok increases, errors=0 → the adaptive governor thinks load is being delivered with no evidence the target received anything.

Severity: P1 — metric and adaptive-control correctness

Smallest correct fix: use a vector-neutral operation model (operations_started/completed/failed, bytes_sent/received) and define vector-specific "completed" semantics (HTTP=headers received, TLS=handshake done, UDP=datagram handed to kernel, raw=packet handed to transport, TCP-exhaust=connection established, Slowloris=partial request established). The report should say what actually happened, not label local packet enqueue as a response.

## P1 — the adaptive governor is not actually per-vector

src/engine/mod.rs:727-747 — each vector gets its own Governor, but all governors read the same global `metrics.responses_ok` / `metrics.errors`.

Concrete failure: HTTP flood + Slowloris + RUDY. Slowloris starts getting connection failures; HTTP traffic still healthy; global error rate exceeds 50%; HTTP governor halves its concurrency; RUDY/Slowloris governors also react to the same aggregate. The system can't answer "which vector caused the distress?" nor adapt each vector to its own behavior.

Severity: P1 — control-loop correctness

Smallest correct fix: give each vector its own VectorMetrics { operations_started, completed, failed, latency_histogram }; each governor consumes only its vector's metrics. If cross-vector coupling is intended, call it a global governor. Current code claims per-vector control but implements global feedback duplicated across governors.

## P1 — 2700 is not defensible as a universal fixed concurrency

src/presets.rs:16, :93-109 — the comment claims 2700 stays inside one box's local limits. Not generally true. ulimit -n may be 1024. The router preset has 2700 SYN + 2700 ACK + 2700 TCP-exhaust; the tcp-exhaust portion alone exceeds a common 1024-FD limit. The CDN preset has 8,100 workers across three vectors.

Severity: P1 — design correctness and measurement validity

Smallest correct fix: replace fixed concurrency with a local-resource budget (safe_fd_budget, safe_ephemeral_port_budget, safe_memory_budget, safe_conntrack_budget). Before the run: inspect RLIMIT_NOFILE, ephemeral port range, existing FDs; account for one socket per worker; refuse or cap configurations that cannot be represented locally. Principle: the tool must know when it is measuring the target vs when it has saturated itself. 2700 may be useful on one machine; it is not a universal safe level.

## P1 — the configured proxy is silently ignored

src/config.rs:235-245; cli.rs:112-124; engine/mod.rs:163; engine/net.rs

The CLI configures `socks5://127.0.0.1:9050`, stores it, prints it in the summary — but the engine never uses it. `Target::resolve()` resolves directly and all traffic uses `TcpStream::connect(self.addr)`. Recon uses a direct reqwest::Client. Operator sees "proxy: socks5://..." and reasonably believes traffic is routed through it. It is not.

Severity: P1 — silent configuration failure

Smallest correct fix: until proxy support exists, `if cfg.proxy.is_some() { return Err("proxy configuration is not supported by the engine"); }`. Failing loudly is much safer than printing a proxy config that has no effect. If implemented later, distinguish proxy-capable L7 vectors from raw L3/L4 vectors that cannot use a SOCKS proxy.

## P1 — "sustained degradation" is not actually sustained

src/engine/mod.rs:834-849 — docs say "sustained 3× breach" but the code triggers on one 250 ms sample (`if p99 > base*3.0 { degraded_at = ... }`). classify.rs:206-245 uses `peak_p99 = max(all samples)`, so a single spike can produce Degrading.

Concrete failure: baseline p99=10ms, one transient sample=100ms, every later sample=12ms → still classified Degrading with a derived time-to-degradation.

Severity: P1 — false finding / dishonest collapse curve

Smallest correct fix: require N consecutive samples above threshold (or ≥ X seconds). Use hysteresis: enter degraded >3× baseline, recover <1.5× baseline for N consecutive samples. You already describe hysteresis-like behavior; the implementation needs to enforce it.

## P1 — stop_on_detect compares incompatible baselines

src/main.rs:194-198; engine/mod.rs:635-640 — `ctx.baseline_ms` comes from recon (HTTP TTFB) but `detect_monitor()` compares it against TCP connect latency. Example: recon TTFB baseline=120ms, TCP connect baseline=4ms → threshold ≈ 3×120+25 = 385ms, meaningless for a 4ms connect.

Severity: P1 — incorrect stop-on-detect behavior

Smallest correct fix: use `probe_baseline_ms` for probe latency decisions; use `ctx.baseline_ms` only for application request latency. Never compare a TCP-connect baseline to an HTTP-TTFB observation.

## P2 — the sampler's RPS is wrong whenever the runtime delays the sampler

src/engine/mod.rs:770-800 — RPS is `d_ok / 0.25`, assuming every interval is exactly 250ms. Tokio timers aren't real-time; under load the sampler may run after 500ms/1s. 1000 completions over 1s ÷ 0.25 → reported 4000 vs actual 1000.

Severity: P2 — metric distortion

Smallest correct fix: `let dt = now.duration_since(last_sample); rps = delta / dt.as_secs_f64();`. Same for any time-window rate metric.

## P2 — raw and UDP "RPS" is not response RPS

Answer to your first recent-fix question: deriving RPS from completions is right for HTTP (with the accounting caveat), but not for all vectors globally. For UDP/ICMP/raw SYN/ACK there is no application response — responses_ok means "local send syscall succeeded" and should be called packets_sent_per_second. For Slowloris/RUDY/SlowRead/TCP-exhaust the meaningful rate is connections_established/sec or connections_held. A single RPS number is not a universal abstraction for 16 radically different vectors.

## P2 — the 50 ms HTTP reconnect backoff is damage control, not a universal "right" value

src/engine/http_flood.rs:17-20 — directionally correct (previously connect→reset→reconnect with no delay could make the client the bottleneck). But 50ms is fixed policy = 20 reconnect attempts/sec/worker; at 2700 workers that's still enormous reconnect pressure. The Ok(false) vs Err distinction is good. More correct design: classified backoff — transport error → exponential backoff with jitter, capped; clean keep-alive close → reconnect normally; successful response → reset backoff. Reconnect rate should be bounded by the client-side resource budget, not an arbitrary constant.

## P2 — the errno handling is Linux-specific and the "target failure" category is too broad

src/engine/mod.rs:511-569 — local-resource mappings are sensible for Linux but hardcode Linux errno numbers without `cfg(target_os = "linux")`. Not portable. Also `_ => TargetFail` treats every other connect error as target-side, including local routing/namespace/firewall/interface/path failures. The code measures "connect attempt did not succeed and wasn't one of four known local-resource errors," not "target failure."

Smallest correct fix: platform-aware classification; name the category honestly (ConnectFailure::RemoteOrPathFailure) unless evidence proves the target caused it.

## P2 — recon's "same host" invariant is weaker than "same origin"

src/recon/crawl.rs:45-53 — checks `resolved.host_str() == base_host` but not scheme or port. `https://target.example:8443` can lead to `http://target.example:80` and pass. Fix: scope = scheme + host + effective port, enforced exactly.

## P2 — recon discovers POST forms but measures them with GET

src/recon/mod.rs:80-82, :105-145 — recon preserves method="POST" but `timed_ttfb()` always does `client.get(url)`, and the engine's vector config doesn't carry the method. So the tool can recommend `POST /expensive-endpoint` based on one behavior while actually flooding `GET /expensive-endpoint` — undermining the asymmetry thesis. Fix: implement method-aware recon+execution (with safe body templates), or only rank GET endpoints until non-GET execution is supported. Don't display a method as tested when it wasn't.

## Good decisions worth keeping

- Replacing requests_sent-based RPS with completion-oriented accounting was the correct direction for HTTP reset churn.
- Separating local exhaustion from remote/probe failure was a real improvement; the previous false-DOWN path was genuinely dangerous to classifier credibility.
- The watch shutdown channel is a good primitive — the problem is that not every blocking op races it.
- Confidence cap below 1.0 is good epistemic hygiene.
- Single-origin/no-spoofing architecture is substantially more credible than pretending one host reproduces distributed volumetric DDoS.
- The evidence trail is the right résumé differentiator.

## Verdict on the three recent fixes

1. Completion-based RPS — correct for completed HTTP transactions, not as one universal metric across all vectors. Right architecture: per-vector operation metrics → vector-specific throughput → common report schema. Biggest remaining bug: one logical HTTP operation can increment both responses_ok and errors.
2. 50ms reconnect backoff — good fix, but a fixed 50ms is only a safety floor. Use bounded exponential backoff for repeated transport failures, reset after successful progress.
3. ECONNREFUSED as "up" — defensible for host reachability; wrong for service availability after a successful baseline. Correct model: ECONNREFUSED = host responded, service not accepting this connection; whether it's a finding depends on baseline. The classifier currently throws that distinction away.

## The single change that would most improve credibility

Build a real independent control-plane measurement path. Right now the tool mostly asks: did the same machine that generated the attack traffic still manage to TCP-connect? Add a separate observer (control request + TCP/connect latency + service-level success rate), independently scheduled or externally hosted, so the report can distinguish "target degraded" from "the load generator exhausted itself." If a second machine isn't wanted, at minimum a dedicated control-plane client with separate resource accounting and a separate runtime/thread issuing a real application-level health request for HTTP targets. Then: "This tool does not merely generate load. It independently measures whether the service remained usable while the load generator was operating."

I would not call the current classifier trustworthy enough for a résumé claim of reliable resilience verdicts until the P0/P1 issues above are fixed.
